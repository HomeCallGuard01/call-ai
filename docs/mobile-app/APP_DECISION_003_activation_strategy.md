# APP_DECISION_003 — Activation Strategy

STATUS: **LOCKED — real-device-verified 23 Aug 2026.** This document's original iOS conclusion (§"Confirmed facts", below) is superseded by direct physical-device evidence — see "Correction" immediately below. Do not treat the original research as authoritative for the one-tap question; it is retained only for its still-accurate carrier/provider findings (§UK mobile carriers, §UK landline).

## Correction (23 Aug 2026) — the one-tap `tel:` mechanism works on iOS, empirically confirmed

This document originally concluded "there is no path — app, Shortcut, or otherwise — for an iOS app to activate call forwarding without the customer manually opening the Phone app and dialling a code themselves," based on a literal reading of Apple's own `tel:` documentation ("the Phone app will not attempt to dial" a string containing `*`/`#`).

That reading was too strict. Separately, commit `af8d3ba` (`sandbox/mobile-app-v1`, 5 Aug 2026, `mobile/lib/dialerLink.ts`) built and shipped (to the mobile app only, never the website) a `tel:` link mechanism — `tel:` + the code with every `#` percent-encoded to `%23`, `*` left literal — on the theory that Apple's restriction blocks *silent/automatic* dialling, not a pre-filled confirmation the customer must explicitly accept. That commit's own tests were unit-level only; no real-device confirmation of the dialer-opening behaviour itself was ever recorded in this project's history until now.

**23 August 2026, real physical iPhone, isolated test (no app, plain Safari + a static test page reproducing `af8d3ba`'s exact `buildDialerUrl` logic):** tapping the button produced the native iOS "Call 21..." confirmation with the complete code correctly pre-filled; pressing Call resulted in the carrier's own confirmation screen: **"Setting Activation Succeeded – Voice Call Forwarding On All Calls."** This is unambiguous, direct evidence the mechanism works, on real iOS, from a real website (not just a native app) — it is not restricted to native apps, since Safari and `Linking.openURL` both resolve to the same underlying `tel:` URL handoff.

**What this means for the two documents:** they were not actually describing contradictory technical realities — Apple's own restriction is real (it blocks fully *automatic*, no-confirmation dialling), but `af8d3ba`'s approach never claimed that; it always required the explicit Call-button tap this test just confirmed still works end-to-end. §"Recommended activation design" below (particularly points 2 and 5) is the part that no longer holds and must not be followed for iPhone/Android going forward — see the new §"Revised activation design (23 Aug 2026)" underneath it.

## The core constraint, stated plainly

Home Call Guard's actual product — AI reasoning over what a caller *says* — requires the call's audio to reach Twilio. That requires the customer's real number to divert to a Twilio-owned number. **This is true on every platform.** No mobile app, on either OS, can make this requirement disappear, because the screening isn't "is this number on a blocklist" (which could theoretically happen on-device) — it's "is this specific conversation, right now, asking for a password" (which requires the call to actually be answered somewhere that can hear it). This was independently re-confirmed this session via direct research into both platforms' current capabilities — see the Confirmed Facts section below.

The entire activation-strategy problem is therefore: **how do we make "set up call diversion" as close to zero-effort as each platform genuinely allows** — not how do we eliminate it.

## Confirmed facts (researched this session, cited)

**iOS:** Apple's own `tel:` URL scheme documentation states the Phone app will not attempt to dial any string containing `*` or `#` — which rules out GSM/MMI forwarding codes (all of which are built from `*`/`#`) from being triggered via any in-app deep link, confirmation dialog or otherwise. This is stated by Apple to be deliberate, specifically to prevent apps from "maliciously redirecting phone calls or changing the behavior of a phone or account." Independently confirmed via real-world testing (iOS Shortcuts cannot dial MMI codes either). **There is no path — app, Shortcut, or otherwise — for an iOS app to activate call forwarding without the customer manually opening the Phone app and dialling a code themselves.** ([Apple Developer — Phone Links](https://developer.apple.com/library/archive/featuredarticles/iPhoneURLScheme_Reference/PhoneLinks/PhoneLinks.html), [MMI dialling from iOS Shortcuts — confirmed unsupported](https://gist.github.com/jdgregson/a16b3dc069d2e85bca1c5f218ba25083))

**Android:** has a genuine native capability iOS lacks — `CallScreeningService`, which lets a designated app intercept incoming calls *before they ring* and decide to allow/silently reject them, with a 5-second response budget. This is real and worth using — but it operates on **caller-ID metadata only** (the number, plus a STIR/SHAKEN verification verdict if the app is the default caller-ID/spam handler), not on call audio or conversation content. It cannot replace Home Call Guard's core "listen and reason" screening — it *could* support a fast, pre-ring "known scam number" blocklist layer as a complementary feature, but the core product still needs the call routed through Twilio regardless. ([Android Developers — Screen calls](https://developer.android.com/develop/connectivity/telecom/dialer-app/screen-calls), [CallScreeningService reference](https://developer.android.com/reference/android/telecom/CallScreeningService))

**UK mobile carriers (EE, O2, Vodafone, Three):** all use the same 3GPP-standardised GSM supplementary-service codes (`*21*<number>#` unconditional forward, `#21#` to cancel, `*#21#` to check status) — this is a telecom standard, not carrier-specific behaviour. There is no meaningful technical difference between the four for this purpose; any carrier-specific "activation process" documentation would mostly be redundant across them.

**UK landline (BT, Sky, TalkTalk, Plusnet):** use the **identical** `*21*<number>#` code format, dialled from the landline handset — a genuinely useful, non-obvious finding: mobile and landline activation instructions can largely be unified into one piece of copy. **Two real exceptions:** Virgin Media requires an extra leading `0` (`*21*0<number>#`) and both **Sky and Virgin Media require calling 150 first to add "Call Divert" as an account feature** (Sky: ~£2.50/month) before the code will work at all — this is a genuine per-provider difference worth surfacing explicitly in onboarding rather than assuming one universal instruction covers everyone. ([UK call-diversion code reference, cross-provider](https://connection-technologies.co.uk/help/apn-settings/divert-landline-calls-to-mobile-uk-codes-for-bt-sky-virgin-voip))

## Recommended activation design

1. **Ask the customer's phone type and provider up front** (a two-tap picker: iPhone/Android/Landline, then provider if landline) — this determines exactly which instructions and caveats to show, rather than one generic paragraph.
2. **Show the exact code, large, with a "copy code" button** and a plain-language explanation of what dialling it does (this can't be automated on iOS at all; Android gains nothing from automation here either, since diverting a call is an MMI action on Android too — Android's `CallScreeningService` is a *different* capability, not a way to auto-dial forwarding codes).
3. **Verification, not automation, is where effort should go.** The app cannot activate forwarding, but it *can* confirm it worked: prompt the customer to place (or receive) a test call immediately after dialling the code, and use the real `calls` table / a dedicated verification endpoint to confirm a call actually routed through Twilio successfully — turning "did I do this right?" (the actual source of customer anxiety here) into a clear pass/fail the app can show within seconds, rather than leaving the customer to wonder.
4. **Sky/Virgin get an extra, explicit step** ("call 150 first") surfaced before the code, not buried in a footnote — this is the one place per-provider divergence genuinely matters.
5. **Explicitly do not promise "one tap setup"** anywhere in copy — Apple's own platform restriction makes that a claim the app cannot honestly make on iOS, and inconsistent copy between platforms would undermine trust with the exact audience (older, non-technical) that most needs to trust the instructions the first time.

## What this means for effort allocation

The "verification" layer (point 3) is where real engineering effort should go for this feature — it's the one place the app can add genuine value beyond what a static help page already provides, and it directly serves the stated goal (reassuring, simple, polished) better than chasing automation the platforms don't allow.

## Revised activation design (23 Aug 2026, real-device-verified for iOS)

Supersedes points 2 and 5 above for iPhone/Android specifically. Points 1 (ask device type), 3 (verification), and 4 (Sky/Virgin) still stand as written — landline is explicitly unchanged and out of scope for this revision (the forwarding code must still be dialled from the physical landline handset, a different device entirely; see `mobile/lib/dialerLink.ts`'s own `canAutoOpenDialer`, which correctly excludes landline).

1. **No visible code, no Copy button, no MMI/forwarding terminology for iPhone/Android.** One primary action: **"Get Protected Now."**
2. Device type (iPhone vs Android) is detected automatically from the browser's own user agent where the customer is completing setup on the device being protected (the common case) — no picker step needed. Landline remains an explicit, separate choice (a landline can't be detected from a browser, and isn't the device being browsed on).
3. Tapping the button: fetch the real code from the existing `/activation-instructions` endpoint (unchanged backend, still server-generated, still never displayed), build `tel:` + code with `#` percent-encoded exactly as `af8d3ba` does, and navigate to it immediately — no intermediate "here's your code" screen.
4. Before the tap, brief, honest expectation-setting copy: the phone will show a call confirmation, press Call, and Apple/the carrier may show its own "Setting Activation Succeeded" confirmation with a Dismiss button — explicitly reassure the customer that Dismiss does not undo protection.
5. Returning to the site (Page Visibility API, matching the mobile app's `AppState` listener pattern) auto-triggers the existing `/activation-verify` check — no manual "I've done this, check now" tap required.
6. **Android parity is not yet claimed or verified.** `af8d3ba`'s `canAutoOpenDialer` returns true for Android too, and there's a reasoned technical case it should work the same way (Android's `tel:` links resolve to `ACTION_DIAL`, handing off to the Phone app for explicit confirmation — a different code path from the `sendUssdRequest()` API that Android 17 QPR2 specifically hardened in August 2026), but this must be confirmed on a real physical Android device before the same claim is made for Android customers. Until then, treat Android as "implemented, same mechanism, pending its own real-device confirmation" — not yet a locked decision the way iOS now is.
