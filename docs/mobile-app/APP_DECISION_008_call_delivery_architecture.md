# APP_DECISION_008 — Call Delivery Architecture (Self-Protecting Return Path)

STATUS: LOCKED — implemented 23 Aug 2026. Companion to APP_DECISION_003 (activation strategy) — that document covers how forwarding gets turned on; this one covers where an approved call actually goes once it does.

## The incident this closes

Production's first real forwarded call, 15 Aug 2026, looped indefinitely: an approved call was dialled back to `household.phone_number` over PSTN, which still had the customer's own unconditional carrier forwarding active to the same Twilio number — the carrier intercepted Twilio's own dial-back and redirected it straight into a brand-new inbound call, forever. Full incident: `docs/operations/HANDOVER_2026-08-15.md` §6-13.

A same-day fix (`fix/call-forwarding-loop-2026-08-15`, commit `b2a8924`) attempted to guard this using Twilio's `ForwardedFrom` request parameter. **Confirmed dead code, 23 Aug 2026**: real Twilio Console Request Inspector data for two actual forwarded calls shows `ForwardedFrom` absent on this UK carrier path. A guard conditioned on a parameter the carrier never sends can never fire. This branch was never merged into `main`.

## The decision

**The loop is made impossible by construction, not by a runtime check.** `households.self_protecting boolean not null default true` (migration 028) is an explicit, stored fact — never inferred by comparing phone numbers at call time, never dependent on any Twilio-supplied parameter.

- **Anything except an explicit stored `self_protecting === false`** (the default `true`, `null`, `undefined`, a missing column on not-yet-migrated data, a malformed non-boolean value): the household's own phone is treated as both the forwarded line and the intended recipient. `services/callRouting.js`'s `decideCallDeliveryPlan` returns `{ mode: "client-only" }` — no PSTN number is ever constructed anywhere in this code path. Delivery is exclusively via a Twilio Voice SDK `<Client>` noun to the Home Call Guard app (`client:household_<id>`), which never touches the PSTN/carrier-forwarding layer at all, so the loop condition cannot occur regardless of carrier behaviour. If the Client doesn't answer (app not installed, not registered, or timed out), the call fails safely (`/call-delivery-failed`, a plain "please try again later" message) — it never falls through to a PSTN dial-back. **Tightened 23 Aug 2026, same day as the original version**: the first implementation treated a *missing* self_protecting field as safe to PSTN-dial (backwards — absence of data must never be read as permission). `decideCallDeliveryPlan` now requires the one positive, explicit value below to ever unlock PSTN; every other state, including "we don't know," is self-protecting.
- **`self_protecting === false` only** (a genuinely separate destination — a different family member's line, a landline monitored by someone else): PSTN `<Number>` delivery remains valid and unchanged, since the destination is confirmed distinct from whatever's actually forwarded. `<Client>` is still offered in parallel as a bonus.
- **Standard onboarding never asks the customer to understand or choose this** — the normal customer is not expected to know what "self-protecting" means. `self_protecting` defaults to `true` for every household; only a distinct, not-yet-built "I'm protecting someone else's phone" journey would ever set it `false`. Until that journey exists, every real household is correctly on the safe-by-default path.

## Why this, not the app-vs-website question

The earlier framing of this problem as "does call delivery require the app" was incomplete. The real constraint is narrower and unconditional: **a self-protecting household can never safely receive an approved call over PSTN, regardless of which client (website or app) configured activation.** The one-tap website activation mechanism (APP_DECISION_003) and this delivery decision are independent — a customer can activate forwarding entirely through the website, and still requires the app's Voice SDK registration to actually receive the resulting approved call. "Do not claim Protected until forwarding AND the required app call-delivery endpoint are actually ready" (product requirement, 23 Aug 2026) follows directly from this.

## Platform status

- **Android:** real-device proven (`sandbox/mobile-app-v1` commit `5069d42`) — FCM push delivery, real incoming-call UI, manual answer, two-way audio, confirmed twice on a physical Moto E7.
- **iOS:** client code already correct (`mobile/lib/voiceClient.ts` calls `voice.initializePushRegistry()`, delegating CallKit/PushKit integration to Twilio's SDK; `aps-environment: production` and `UIBackgroundModes: ["audio", "voip"]` already configured). **Blocked on one missing resource**: no Twilio iOS Voice Push Credential has ever been created (`TWILIO_VOICE_PUSH_CREDENTIAL_SID_IOS` absent from every env file) — an owner-only action (Apple Developer Portal APNs key + Twilio Console), not a code gap. Real-device proof pending as of this document's status date.

## What was NOT built today (explicitly deferred)

Customer notification (voicemail/SMS/missed-call alert) for the case where an approved call reaches `/call-delivery-failed` — the household currently gets no notification at all when this happens. Logged as a real, known gap; not built as part of this decision, to keep this change scoped to the routing/delivery-safety fix it's actually about.

## Update, 2026-09-07 — reachability gate, delivery-verified evidence, protection-status hardening

Production evidence (2026-09-07) found a second, independent gap in the design above: `self_protecting` alone unlocked client-only delivery with **no check that a Voice SDK client was actually registered and reachable** — true only for one internal test device, false for every real household, since no customer-facing app has meaningfully shipped yet. 27/27 real client-only delivery attempts across production had failed, with 0-second-duration `no-answer` on the Client leg — Twilio's signature for "no client is registered under this identity at all," not a genuine unanswered ring.

**Fixed**: `households.voice_client_registered_at` (new migration) + `isVoiceClientReachable()` (`services/callRouting.js`) — `decideCallDeliveryPlan` now requires current, real registration evidence (reported by `mobile/lib/voiceClient.ts`'s `performRegistration()` via `POST /api/v1/voice/registered`, TTL 3600s + 15min grace) before ever choosing `client-only`; otherwise a distinct, alertable `self-protecting-unreachable` outcome — still never PSTN.

**Also fixed, same release**: `households.delivery_verified_at` (new migration) — real Twilio evidence (`DialCallStatus === "completed"` on the actual Dial leg) that an approved call connected, as the *only* thing that can justify a "You're protected" claim to a customer. `activation_verified_at` (proves only the inbound leg) and Voice SDK reachability (a capability fact, not proof of delivery) were both found, independently, to have been silently treated as sufficient for this claim — neither is, on its own. `services/callRouting.js`'s `computeProtectionStatus` now keeps three states distinct (`forwardingVerified` / `deliveryReady` / `endToEndDeliveryVerified`) and only `fullyProtected` (requiring current reachability **and** real delivery evidence) may ever be shown to a customer as "protected." Two customer-facing screens were found making an unconditional protection claim independent of any of this (`upload.html`'s onboarding-checklist card, the mobile app's setup-complete screen) and corrected to accurate, non-overclaiming wording.

**Shared-device fix**: `mobile/lib/voiceClient.ts`'s module-level `registered` flag was never reset on sign-out, meaning a second household signing into the same physical device after the first signed out would silently never re-register under its own identity. Fixed (`resetVoiceRegistrationState()`, called from the account screen's sign-out handler).

## Update, 2026-09-08 — landline PSTN delivery: designed, then deferred before release

A separate delivery path for explicitly-classified landline households was designed and implemented alongside the above: `households.device_type` (customer-entered `iphone`/`android`/`landline`, persisted from the existing activation-instructions selection) driving a `pstn-only` mode in `decideCallDeliveryPlan` for landline households — reasoning that a landline's own on-file destination number is not the number that's carrier-forwarded to Home Call Guard, so plain PSTN dial-back carries none of `self_protecting`'s loop risk.

**Found, before shipping, that device_type alone is not sufficient proof of loop safety** — a customer could select "landline" for what's actually a self-forwarding mobile line. A runtime guard was then built reusing `services/phone.js`'s existing `wouldCreateForwardingLoop()`, comparing Twilio's `ForwardedFrom` request parameter (real, live evidence of which number forwarded a given call) against the landline destination before ever building the PSTN `<Dial>`.

**Read-only production evidence (2026-09-08) found this guard cannot currently work**: queried Twilio's real Calls resource directly — 184/184 genuine inbound calls in this account's history had `ForwardedFrom` populated, but in **every single case** its value was the Twilio number itself (`To`), never the actual diverting line. No other field on the Call resource carries diversion-source information. A guard built on this signal can structurally never detect a real loop (the two compared values can never be equal), while the code would read as if safety were proven — false assurance, not real protection.

**Decision**: `households.device_type`, its persistence RPC, the `pstn-only` and `landline-loop-unsafe` delivery modes, and the `ForwardedFrom`-based guard were all removed from this release before shipping — none of it was ever applied to any database, and no landline household exists in production today. Every household — landline or mobile, classified or not — is currently treated identically and conservatively: `client-only` when a Voice SDK client is provably reachable right now, otherwise a safe, alertable failure, never PSTN.

**Smallest safe alternative for a future landline release, proposed not built**: stop trying to prove loop safety per-call from Twilio-supplied data (no reliable live signal exists for it in this environment), and instead require a one-time, explicit, customer-confirmed distinct number at classification time — reusing `wouldCreateForwardingLoop()` exactly as it already runs today on `/activation-instructions`'s `protectedNumber` input-validation check, except *persisting* that proof at classification time rather than only using it for one-off UI validation. Not implemented as part of this update.
