## 6. Latest production call failure: the screening loop

**Symptom:** forwarded call reaches Home Call Guard, plays the
protected/monitoring prompt, caller states their reason — instead of
connecting, it goes back to the start and asks again. Repeats.

**Root cause (high confidence, see §7 for the one unverified assumption):**
Not a control-flow bug in `/voice` or `/process` — both handlers were read
in full and contain no redirect/re-gather loop. The actual sequence:

1. `/voice` → unknown caller → `<Gather action="/process">` asks reason.
2. `/process` → classified SAFE (confirmed via real production data:
   `ai_model: gpt-4o-mini`, correct ~1.2–2.5s processing time — the
   classifier genuinely ran, this is not the earlier keyword bug) →
   returns `<Start><Stream>` (live monitoring) + `<Dial><Number>+447715562700</Number></Dial>`.
3. Twilio dials `+447715562700` — but that number still has unconditional
   CFU active to `+441322946885`. The carrier intercepts Twilio's own
   dial-back attempt before it rings, and redirects it straight back to
   `+441322946885`.
4. That redirect arrives as a **brand-new inbound call** (new Call SID) →
   hits `/voice` again → asks the reason again. Repeats indefinitely.

**Two real Call SIDs observed** (20s apart, same household, same `From`,
both classified SAFE, both independently started a live-monitoring Media
Stream that reached double-digit transcript chunks — direct proof the
`<Dial>` was genuinely attempted both times, not skipped):

- `CA0b720c3004a6f59f0db5f5298779f22d` — 2026-08-15 13:15:37.162 UTC
- `CAc53453e3a12820240b722175ed5e9fe4` — 2026-08-15 13:15:57.576 UTC

This bug is **pre-existing and unrelated to the live-monitoring port** —
`services/callRouting.js`'s `resolveForwardingDestination()` was unchanged
by that port. It was never triggered before because the old keyword
classifier almost always misclassified real calls as SCAM, so `<Dial>` was
never reached. Fixing the keyword bug (§2.1) is exactly what exposed this
one for the first time.

## 13. Product-architecture gap (bigger than a routing bug)

Investigated without changing any code, per explicit instruction. Answers
grounded in the actual onboarding copy and codebase, not assumption:

**What does `households.phone_number` mean today?** Both "protected
number" and "safe-call destination" simultaneously — by design, not
mistake. `upload.html` (~line 1049) presents *one* input field
(`householdPhoneNumberInput`) under "What number should protected calls
ring?", and the very next section, using that same value, says "Turn on
call forwarding" → "Dial this on the phone you're protecting." One DB
column, one onboarding field, two roles the architecture assumes are
always the same number.

**What does onboarding tell the customer to enter?** Their own phone
number — then instructs them to dial `*21*<HomeCallGuardNumber>#` on that
exact phone (`services/activationInstructions.js`, `buildActivationInstructions`).
No second field exists anywhere in web or mobile onboarding for a
different destination number.

**For a normal one-mobile customer, how does a SAFE call reach them after
CFU is active?** It doesn't, via the current mechanism. Once unconditional
forwarding is active (as onboarding instructs), that number is intercepted
by the carrier for every incoming attempt, including Home Call Guard's own
outbound `<Dial>` back to it. This is exactly what happened twice, back to
back, in today's real incident (§12). This is not a misconfiguration by
this one customer — it is what onboarding tells every customer to do.

**Does V1 have another delivery mechanism (VoIP/app-based)?** No. Grepped
`mobile/`, `services/`, `routes/` for CallKit/PushKit/VoIP/Twilio-Voice-SDK/
any app-based call-answering path — nothing exists. The only implemented
"connect" mechanism, for both known contacts and SAFE unknown callers, is
a plain PSTN `twiml.dial().number(household.phone_number)`
(`server.js`'s `dialHouseholdOrFailClosed`). Checked
`docs/DECISIONS.md`, `docs/ARCHITECTURE.md`, `docs/launch/KNOWN_ISSUES.md`
— none mention this conflict; it is not a previously-known/accepted
limitation, it's a genuinely new finding from today.

**Bottom line:** as V1 is currently built, a customer who follows the
product's own onboarding instructions on a single mobile phone can never
have a SAFE call actually reach them by voice — the dial-back is
structurally guaranteed to loop into the forwarding they were told to set
up. The `ForwardedFrom` guard (§1, §12) is a necessary safety net to stop
the runaway loop/cost on carriers where it does fire, but it is NOT
sufficient, and does not touch this underlying gap. This needs a product
decision — e.g. a genuinely separate second number field (landline, family
member, etc.), or an app-based delivery mechanism (Twilio Voice SDK /
push-to-answer in the mobile app) — a materially bigger scope than a
"minimum safe fix." **Do not implement anything here without the user
explicitly choosing a direction.**

### 20.1 EAS / build setup

**EAS project creation.** No EAS project existed yet under the
`homecallguard` account for this app. Created via `eas init --force`
(safe — verified first via `eas init` without `--force` that nothing
existing would be duplicated: it errored "Project does not exist", proving
there was nothing to collide with). Project: `@homecallguard/home-call-guard`,
ID `ef830297-a578-405e-b762-16f68e3097ba`, written into `mobile/app.json`'s
(later `app.config.js`'s) `extra.eas.projectId`. Package ID
`co.uk.homecallguard.app` was never changed at any point across the entire
session, including through every rebuild.

**SDK 54 dependency alignment.** `expo install --check` (Expo's own
compatibility tool) is the fastest way to catch drift — run it *before*
troubleshooting an opaque native build failure, not after. It flagged four
packages simultaneously out of alignment with the installed `expo@54.0.0`:
`expo-dev-client`, `@types/react`, `typescript`, `@react-navigation/bottom-tabs`.
`expo install --fix` corrected all four in one shot.

**`expo-dev-client` mismatch.** Found at `^57.0.12` (a completely
different generation than SDK 54 uses); the compatible version is
`~6.0.21`. This exact mismatch is what caused the very first Gradle build
failure: `expo-dev-menu:compileDebugKotlin FAILED` — `Unresolved reference
'OptimizedRecord'` and `onDidCreateReactActivityDelegateNotification
overrides nothing`. Both errors are native Kotlin symbols that only exist
in the *wrong* `expo-modules-core` API generation — a version mismatch,
not a code bug, and `expo install --fix` was the complete, correct fix.

**npm 10.8.2 vs npm 11 lockfile incompatibility — the most expensive single
lesson of the day.** This machine's local npm is 11.x (bundled with
Node 25). EAS Build's cloud image runs **npm 10.8.2**. A `package-lock.json`
regenerated locally with npm 11 can pass `npm ci` locally and still fail
`npm ci` on the EAS builder with a *misleading* "package.json and
package-lock.json … not in sync" error that has nothing to do with the
actual dependency versions — it's a lockfile-serialization compatibility
gap between npm major versions. **Always regenerate `package-lock.json`
with the exact npm version the target builder uses**
(`npx -y npm@10.8.2 install`), then verify with
`npx -y npm@10.8.2 ci --include=dev` locally before ever pushing to a
cloud build. This single fact cost two full failed EAS builds before being
identified.

**Duplicate/conflicting dependencies found.** `package.json` had `typescript`
and `@types/react` each listed *twice* — once under `dependencies` (correct
range) and once under `devDependencies` (wrong, newer range) — an
`npm ci` `EUSAGE` error ("Missing: typescript@5.9.3 from lock file"). The
first fix attempt (removing the `dependencies` entries, keeping
`devDependencies`) was the *wrong* choice — verified only later, via
`expo install --check`, that the `dependencies`-side versions (`~5.9.2`
typescript, `~19.1.10` `@types/react`) were the SDK-54-correct ones all
along. Lesson: when two conflicting version ranges for the same package
exist, don't guess which one is "idiomatic" — check `expo install --check`
first, it knows the actual correct answer.

**`expo-font` 57.x hoisting problem.** The single most confusing bug of
the day. `expo-font` was never a *direct* dependency, so
`expo install --check`/`--fix` never flagged it — but npm's
auto-peer-dependency resolution hoisted it to **`57.0.1`** at the top
level (where Android's native autolinking reads from) to satisfy
`@expo/vector-icons`'s *unbounded* peer range (`expo-font: >=14.0.4`, no
upper limit), while `expo`'s own correct `~14.0.12` requirement got a
*separate, nested, unused* copy at `expo/node_modules/expo-font`. This
produced a native `NoSuchMethodError` (`ReturnTypeKt.getDirectConverter`)
crash — deterministic, 100% reproducible, survived cache clears, device
reboots, and app-data wipes, because it's baked into the compiled dex, not
runtime state. A full `rm -rf node_modules package-lock.json && npm install`
did **not** fix it — npm re-hoisted the same wrong version from scratch
every time. **Fix: pin `expo-font: ~14.0.12` as an explicit direct
dependency** (`mobile/package.json`), forcing npm's resolver to collapse
the whole tree onto one correct, deduped version. Verified via
`npm ls expo-font` showing a single deduped `14.0.12` everywhere. General
lesson: a transitive package can silently float to the wrong major version
via *another* package's unbounded peer range, invisible to
`expo install --check` (which only audits direct dependencies) — if a
native crash names a class from a specific package, check that package's
*actual* top-level resolved version with `npm ls <package>`, don't assume
range correctness implies resolution correctness.

**`google-services.json` — EAS secret file, not a committed file.**
Committing it was never on the table (Firebase Android config, not
inherently top-secret, but this codebase's convention is real-file
secrets stay local). The actual lesson is about the *EAS Build upload
mechanism specifically*: `.gitignore`-ing the file to keep it out of git
also silently excludes it from **every** EAS Build archive upload,
regardless of whether the build runs in git mode or `EAS_NO_VCS=1` mode —
this produced an "Android prebuild had no file to consume" failure that
looked unrelated to the actual cause. **Fix: upload the file as an EAS
file-type environment variable** (`eas env:set development --name
GOOGLE_SERVICES_JSON --type file --value ./google-services.json
--visibility secret`), and make `app.config.js`'s
`android.googleServicesFile` resolve dynamically:
`process.env.GOOGLE_SERVICES_JSON ?? "./google-services.json"` — the EAS
env var wins on the builder (a real path to the downloaded secret file),
the local gitignored file wins for `expo start`/local prebuild. This
required converting the static `app.json` to `app.config.js`, since a
static JSON file cannot contain a `process.env` expression.

**`.gitignore` vs `.easignore` — they are not the same list, and EAS Build
does not use `.gitignore` the way you'd assume.** Adding
`google-services.json` to `mobile/.gitignore` was the *correct* git-hygiene
move but had the side effect above. A `.easignore` file, if one exists
**at the git worktree root** (not necessarily inside `mobile/`, since
EAS's archiving root is resolved via `git rev-parse --show-toplevel`, not
the directory containing `eas.json`), *fully replaces* `.gitignore`-based
exclusion for archiving purposes — creating one in the wrong directory
(inside `mobile/` instead of the worktree root) silently does nothing.
This was tried, found ineffective, and abandoned in favour of the EAS
secret-file approach above, which sidesteps the whole git/easignore
interaction entirely. If a future need arises to diverge git-exclusion
from EAS-build-inclusion again, remember: `.easignore` location matters,
and get it right on the first try by checking `eas build:inspect -s
archive -o <dir>` locally (dry-run of exactly what would be uploaded)
*before* burning a real cloud build cycle on it.

**The old APK remained installed despite genuine belief the fixed build
had been installed — the single most time-costly false assumption of the
day.** After a successful EAS build with a real fix in it, the user
reported installing it and reconnecting — and the *exact same* already-diagnosed
crash recurred, repeatedly, across a reboot, a full device wipe/re-clear,
and multiple Metro reconnects. Every one of those was a real, honest,
good-faith attempt to install the new build via the Expo web install
link/QR code, and every one of them silently failed to actually replace
the installed APK — most likely because both builds shared the same
`versionCode`/`versionName` (`1.0.0`/`1`, since the `development` EAS
profile has no `autoIncrement`, unlike `production`), which some Android
install flows will silently no-op on ("nothing to update") rather than
error loudly.

**Fix, and now the standing procedure: SHA-256 checksum + install
timestamp is the *only* trustworthy verification, full stop — never trust
"I installed it."**
```
adb shell dumpsys package <pkg> | grep -E "firstInstallTime|lastUpdateTime"
adb shell pm path <pkg> | sed 's/package://' | xargs adb pull -   # then shasum -a 256
# compare against: curl -sL <eas build artifact url> -o build.apk && shasum -a 256 build.apk
```
A changed `lastUpdateTime` alone isn't sufficient proof either — confirm
the *hash* matches the specific build artifact you intend to be running,
every single time, before spending any more diagnostic effort on-device.

**ADB install proved categorically more reliable than the browser/Expo-web
install link for this kind of iterative development testing.** Once the
above was discovered, the fix was: `adb uninstall <pkg>` (forces a clean
slate, sidesteps any same-version no-op logic entirely) then
`adb install <path-to-downloaded-apk>` on the artifact downloaded directly
via `curl`. This was 100% reliable across every subsequent rebuild this
session, with zero repeats of the stale-install problem. **Recommendation
for iOS too:** don't rely on the TestFlight/web-install-link
round-trip for rapid dev-build iteration if `adb`-equivalent (Xcode's
`ios-deploy`/`xcrun devicectl`) tooling is available — verify by hash and
timestamp regardless of install method.

**Motorola launcher: sideloaded app existed correctly in the full app
drawer the entire time, but was never automatically pinned to the home
screen.** This produced a second false alarm ("no icon, must be broken")
that cost real diagnostic time before being traced back to something
mundane: `adb`-installed apps land in the full app list on this launcher,
not automatically on the home screen, unlike a Play-Store-driven install.
Every OS-level check (`pm list packages`, `cmd package resolve-activity
--brief`, `cmd package query-activities`, presence in `dumpsys activity
recents`) was clean throughout — the eventual, correct diagnostic move was
asking the user to specifically open the **full app drawer** (not just
look at the home screen), which found it immediately. Lesson: if every
package-manager-level check says an app is healthy and launchable, but a
human reports "no icon", ask them to check the full app list before
assuming a broken install or a hidden-apps toggle.

**Battery-optimization exemption used during testing.**
`adb shell dumpsys deviceidle whitelist +<pkg>` (equivalent of Settings →
Battery → Unrestricted) was applied once the `52004` push-credential
error was fixed but calls still weren't reaching the device — ruling out
Motorola's aggressive background-app management as a contributing factor
before moving on to the real (Push Credential JWT wiring) root cause. It
did not, on its own, fix delivery — but it's a legitimate standing
exemption worth keeping for any real device used for repeated VoIP-style
push testing, and worth applying proactively for the iOS-equivalent testing
device too if aggressive OS power management is ever suspected there.

### 20.3 Metro / dev-client

**Stale Metro cache after a dependency reinstall caused a real, confusing
bundling failure.** After the `expo-font` fix required
`rm -rf node_modules && npm install`, the *already-running* Metro process
(started before that reinstall) began failing to bundle with `Unable to
resolve ".../metro-runtime/src/modules/empty-module.js" from "_"` — an
internal Metro shim path, not anything in application code. Root cause:
Metro's on-disk transform/haste-map cache (in `$TMPDIR/metro-cache` and
`$TMPDIR/metro-file-map-*`) had gone stale relative to the new
`node_modules` layout, and Metro doesn't reliably auto-invalidate across
an out-of-band `node_modules` change made while it's still running.
**Fix:** stop Metro, delete both cache locations explicitly, restart with
`--clear` (belt-and-braces — `--clear` alone did not appear to be
sufficient on its own until the manual cache deletion was also done).
Confirmed clean via `curl` fetching the actual bundle
(`/node_modules/expo-router/entry.bundle?platform=android&dev=true`)
directly from Metro and checking for `HTTP 200` + a real JS payload,
*before* ever involving the device again — this is a much faster
verification loop than reconnecting a physical phone each time. **Standing
rule: any time `node_modules` changes while Metro is already running,
restart Metro with a full cache clear — don't assume it'll pick it up.**

**Dev-client's connection to Metro is completely independent of Home Call
Guard's own login/auth state, and conflating the two wasted real time
more than once this session.** A device can be fully connected to Metro,
running the current JS bundle cleanly, and simultaneously be logged out
of (or stuck mid-onboarding in) the app itself — these are two entirely
separate layers with separate failure modes. Symptoms like "app shows
Finish Setup" or "nothing happens after reconnect" are *never* Metro
connectivity problems and should never be diagnosed as such; check
`adb logcat` for `ReactNativeJS: Running "main"` (proves JS mounted, i.e.
Metro connection is fine) *before* looking anywhere near auth/onboarding
state for an explanation.

**Reliable procedure that emerged for "confirm the app is in a known-good
state before doing anything else" (use this verbatim going forward,
including for iOS):**
```
1. adb shell am force-stop <pkg>                          # guarantee fresh JS module state —
                                                            # backgrounding/foregrounding alone
                                                            # does NOT reset module-level JS
                                                            # variables (e.g. `registered`)
2. adb logcat -c
3. adb shell am start -n <pkg>/.MainActivity               # lands on the dev-client connect
                                                            # screen — this is expected, not a bug
4. [human] tap the known Metro URL / scan QR, log in, navigate to the real app content
5. adb logcat -d | grep 'ReactNativeJS: Running "main"'    # confirms JS mounted
6. adb logcat -d | grep '<app-specific success marker>'    # confirms the specific thing being tested
```
Skipping step 1 (relying on background/foreground cycling instead of a
full process restart) repeatedly produced ambiguous, silently-stale
results this session — a background→foreground cycle is *not* equivalent
to a fresh process for anything gated by a module-level JS variable.

### 20.5 Twilio Voice SDK

**`GET /api/v1/voice/token` → `404`.** Root cause: the long-running
staging backend process predated the route's addition to
`routes/mobileApi.js` by about 18.5 hours (file `mtime` vs. process start
time, confirmed directly) — Node loads `require()`'d files once at
process start and never re-reads them. **Fix: restart the process.** No
code was wrong; the *running* code was just stale. Verified via direct
`curl` to the route (expect `401` unauthenticated once the route
genuinely exists — a `404` unambiguously means "no such route in this
running process," never a config or auth problem).

**Then `503 voice_not_configured`.** Root cause: `.env.staging` had the
base `TWILIO_ACCOUNT_SID` but none of the three Voice-SDK-specific
credentials (`TWILIO_VOICE_API_KEY_SID`, `TWILIO_VOICE_API_KEY_SECRET`,
`TWILIO_VOICE_TWIML_APP_SID`) — these had been correctly provisioned in
an earlier session but only ever saved into the *other* `.env` file
(production-Supabase-pointing), never copied into `.env.staging`. Fix:
copy exactly those three lines across (values never printed to any log
or terminal output during the copy), restart the backend.

**Firebase Service Account JSON required to create the Twilio FCM Push
Credential — and it is a categorically different, more sensitive file
than `google-services.json`.** `google-services.json` (client-side
Android config, Firebase Console → Project Settings → General → Your
apps) is not sufficient. The Push Credential needs a **Service Account**
key (`"type": "service_account"`, includes a private key and client
email) from Firebase Console → Project Settings → **Service Accounts** →
"Generate new private key" — a different tab, a different file, easy to
conflate on a quick read of "generate a Firebase key."

**Service account JSON must remain secret/gitignored — verified, not
assumed.** It was generated to `/Users/ad/call-ai/<name>.json` (the
*production*-pointing repo root, not this mobile worktree) — confirmed
`git status` showed it as untracked and **not yet gitignored** before any
further action; `*firebase-adminsdk*.json` was added to that repo's
`.gitignore` immediately, *before* the file was read for its `project_id`
or used to create anything. Standing rule for any newly-introduced
credential file: gitignore it before you do anything else with it, not
after.

**Twilio Push Credential created:** SID `CR860503ff17f9d384b46f75726dce61e0`,
type `fcm`, via `client.notify.v1.credentials.create({ type: 'fcm', secret:
<full service account JSON string> })` — the modern FCM HTTP v1 API path
(legacy FCM Server Key strings are deprecated by Google). Confirmed no
duplicate existed first (`client.notify.v1.credentials.list()` → `0`
before creating).

**Twilio error `52004`: "Credential Sid is null, but must be present to
send notifications over FCM."** Found via `call.notifications.list()`
(Twilio's own per-call notifications sub-resource) — this is the specific,
precise diagnostic surface for push-delivery failures; generic call
status (`no-answer`, no `errorCode`) gives zero signal on its own for this
class of bug. Root cause: merely having a Push Credential *exist* on the
Twilio account is **not sufficient** — Twilio has no way to know which
credential to attach to a given client's registration binding unless the
Access Token's `VoiceGrant` explicitly says so. **Fix:** add
`pushCredentialSid: process.env.TWILIO_VOICE_PUSH_CREDENTIAL_SID` to the
`VoiceGrant` constructor in `services/voiceAccessToken.js` (kept optional,
consistent with this file's existing "pure/injectable, not
`process.env`-reading" pattern — the env var is read at the
`routes/mobileApi.js` call site, matching how the other four credentials
are already handled there). Optional rather than required, so environments
without it (including production, untouched throughout) degrade to the
pre-existing behaviour (registration still succeeds, just can't receive a
push) rather than hard-failing.

**Fresh device registration is required after any change to the push
credential/token configuration — the old registration does not
self-heal.** After adding `pushCredentialSid` to the token builder and
restarting the backend, calls continued failing (`52004` gone, but still
silent/no-answer) until the device did a **full fresh registration**
(`registerForIncomingCalls()` re-run from a genuinely clean JS module
state, not just app foreground/background) against the *new* token
shape. A device already holding an old-shape Access Token stays
registered under the old (broken) binding until its TTL naturally expires
or it explicitly re-registers — simply fixing the server-side
configuration does not retroactively repair an already-established
client registration.

### 20.6 Incoming-call behaviour

**Original implementation auto-accepted every `CallInvite` immediately**
(`mobile/lib/voiceClient.ts`'s `Voice.Event.CallInvite` handler called
`callInvite.accept()` directly, by design, for the milestone-1 "prove
two-way audio connects" goal). This is what made the *very first*
successful end-to-end connection ("`status: completed`, real WebRTC
media") misleading on its own — the call connected in ~5 seconds with no
window for a human to perceive a ring at all, and it took the user's own
direct observation ("I did NOT hear the Moto E7 ring") to catch that a
technically-successful connection is not the same as a customer-visible,
answerable incoming call. **Removing the JS-side `.accept()` call
(pure JS/TS, no rebuild) was step one** — it revealed that a *second*,
native-level mechanism was also auto-resolving the call independent of
any JS code.

**Native-level auto-resolution, root-caused precisely:** Android's own
`setFullScreenIntent(pendingIntent, true)` (used by the SDK's
`NotificationUtility.createIncomingCallNotification` to show a
System-style incoming-call UI) can **auto-launch without any real user
tap** — a standard, documented Android mechanism for high-priority
`CATEGORY_CALL` notifications. This app's own code then treats that
auto-launch identically to "user tapped the notification"
(`ACTION_FOREGROUND_AND_DEPRIORITIZE_INCOMING_CALL_NOTIFICATION`), which
explicitly calls `MediaPlayerManager.stop()` — silencing the ringer
before it could ever be heard. This fully explains the "I saw the
buttons flash but heard nothing" symptom, and was confirmed by tracing
the exact native call chain in the SDK's own source
(`VoiceFirebaseMessagingService` → `VoiceService.incomingCall()` →
`NotificationUtility.createIncomingCallNotification` →
`.setFullScreenIntent(..., true)` → OS auto-launch →
`VoiceService.foregroundAndDeprioritizeIncomingCallNotification()` →
`MediaPlayerManager.stop()`), not guessed from symptoms alone.

**Exact patch location and how to reverse it.** A single line removed
from `createIncomingCallNotification` only (two other, unrelated
`setFullScreenIntent` call sites in the same file — for the
already-answered and outgoing-call notifications — were deliberately
left untouched):
```
node_modules/@twilio/voice-react-native-sdk/android/src/main/java/com/twiliovoicereactnative/NotificationUtility.java
  removed: .setFullScreenIntent(piForegroundIntent, true)
  (from inside createIncomingCallNotification() only; .setContentIntent(piForegroundIntent)
   directly above it is untouched, so manually tapping the notification still works)
```
Captured via `patch-package` (not a manual, easy-to-lose `node_modules`
edit): `mobile/patches/@twilio+voice-react-native-sdk+2.0.0-preview.2.patch`,
auto-applied on every install via `"postinstall": "patch-package"` in
`mobile/package.json`. **To fully reverse:** delete that one patch file
and the `postinstall` script line, then reinstall — `node_modules` reverts
to stock SDK behaviour with zero other changes needed. This patch
required one native rebuild (native Android/Kotlin source, not
JS-hot-reloadable) — build `ab9a7ed4-40e1-4f76-9fc5-1718b5a3cb07`, SHA-256
verified installed on the Moto E7 before any further testing resumed.

**Final Android same-phone result, precisely, not overstated:**
- FCM push delivery reaches the device: ✅ confirmed (native
  `onCallInvite` log line + our own JS-side `CallInvite` receipt log,
  both firing with the correct call SID)
- Real Android incoming-call UI (System `CallStyle` notification, red/green
  buttons) appears and **waits** rather than auto-resolving: ✅ confirmed,
  twice, reproducibly, after the patch
- Waits for and responds correctly to a genuine manual answer action: ✅
  confirmed, twice
- Two-way audio / the test confirmation message plays correctly after
  manually answering: ✅ confirmed, twice
- **Audible ringtone before answering: ❌ still silent, confirmed on two
  separate attempts including one where the user deliberately waited
  longer before answering. This is an open, unresolved item — not proven
  fixed by the full-screen-intent patch, and should not be described as
  "ringing" or "the milestone passed" in any future summary until this is
  specifically re-tested and confirmed audible.** Recommendation reached
  this session: retain the patch (it fixed the more serious auto-accept
  defect, and there is no clean pre-patch baseline for ringtone-while-
  waiting behaviour to compare against, since every pre-patch attempt
  auto-accepted too fast to observe it either way) — do not revert it —

    §20.6's entire back-and-forth (auto-accept → patch → still-silent
    ringtone) only happened because Android's milestone-1 code
    deliberately auto-accepted first and added manual-answer proof as a
    separate, later step. For iOS, build (or verify CallKit's built-in
    behaviour provides) a real ring-and-wait experience as the *first*
    thing tested, not a retrofit.
14. **Predetermined test sequence — follow this exact order, don't
    improvise a shorter path:**
    ```
    install → verify build (hash+timestamp) → connect Metro (verify JS mounted)
    → login → verify token (200, correct identity) → verify push registration
    (Voice.Event.Registered, fresh process) → isolated Client call
    (scripts/trigger-voice-sdk-test-call.js, works cross-platform since
    identity is platform-agnostic) → visible/audible ring, genuinely waited
    for → manual answer → two-way audio confirmed
    ```
    Every step in this session's Android work that got skipped or assumed
    rather than explicitly re-verified after a change (stale backend
    process, stale registration after a token-shape change, stale APK
    after a "successful" install) is exactly what produced the debugging
    loops documented in §20. Re-verify the *specific* thing that changed
    after every change, not just "does it still generally seem to work."

## 22. What we should have done differently today

Honest retrospective, specifically to avoid repeating these patterns for
iOS:

- **Verified "installed" and "environment" claims with a hash/log-line
  check from the very first report of unexpected behaviour, not after
  several rounds of re-diagnosing the same already-fixed bug.** The
  single most expensive loop this session (§20.2, old APK silently
  staying installed across a reboot and a full data wipe) could have been
  caught on the *first* recurrence of the exact same crash signature by
  immediately checking SHA-256, rather than re-investigating the crash
  itself as if it were new each time. Lesson generalises: **when a
  supposedly-fixed symptom recurs identically, verify the fix is actually
  the thing currently running before re-diagnosing the symptom.**
- **Assumed a `.env` file's target environment from its filename/log-file
  name instead of the running process's own self-report, once (§20.4)** —
  produced a real, if short-lived, false alarm about production being
  touched. The fix (read the process's own `[env] Loaded environment
  from:` line) was always available and should have been the *first*
  check, not a later correction.
- **Treated "connects successfully" (`call status: completed`, real WebRTC
  media) as equivalent to "the milestone is proven" before the user's own
  direct sensory observation caught that it never actually rang (§20.6).**
  A technical connection succeeding is not the same as a customer-visible
  experience succeeding — this should have been treated as an open
  question requiring explicit human confirmation from the very first
  "completed" status, not asserted as success and only walked back after
  correction.
- **Re-attempted the same background→foreground app-state cycle multiple
  times expecting a different result, instead of recognising early that
  it doesn't reset module-level JS state (§20.3)** — a full
  force-stop-and-relaunch was the reliable move every time it was
  eventually tried; should have been the default from the first
  ambiguous "nothing happened" result, not a late escalation.
- **Didn't check `npm ls <package>` for the actually-resolved version of
  `expo-font` until quite late (§20.1)**, despite the native crash naming
  the exact class involved from the very first occurrence — a
  transitive/hoisted-version check should be an early, cheap step
  whenever a native crash names a specific SDK class, not a last resort
  after cache clears and reinstalls have already been tried and failed.
- **Generally: every one of the above loops shares one root cause —
  trusting an assumption (a claim of "installed", an inferred environment,
  a "successful" connection status, a lifecycle event believed equivalent
  to a fresh process) instead of directly verifying the specific, narrow
  fact in question.** The §21 checklist exists specifically to front-load
  those verifications for iOS before they can cost the same time again.
