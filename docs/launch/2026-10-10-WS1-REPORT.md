## 2. Admin hardening

- **Mutation rate limit.** `middleware/requireAdmin.js` now limits every admin POST/PUT/PATCH/DELETE per verified admin user: 60 per 10 min by default (`ADMIN_MUTATION_RATE_LIMIT`, `ADMIN_MUTATION_RATE_WINDOW_MS`). The response is a 429 with `Retry-After`. This covers every current and future route that mounts `requireAdmin`, with no route-file edits. Reads are never limited.
- **Static guard.** `tests/ws1-admin-route-guards.test.mjs` checks that all 41 `/admin*` routes mount `requireAuth` and then `requireAdmin`. It fails on a new route that doesn't, and on any path-mounted `/admin` middleware.
- **Self-escalation.** On the 075 schema, a signed-in user cannot give themselves the admin role (PGlite R4).

**MFA (decision for Andrew):**

| Option | What | Cost / effort |
|---|---|---|

## 3. Production preflight tooling (read-only by construction)

`scripts/production/preflight-readonly.mjs` prints P3/P4/P5/P6 with PASS or STOP. Guards:
- `--expect-project` is mandatory and must equal `supabase/.temp/project-ref`.
- It refuses to run in `/Users/ad/call-ai`, including through a symlink.
- The CLI allowlist allows exactly: `migration list --linked`, `db query --linked --output-format json` with read-only SQL, and `db push --linked --dry-run`. It refuses push without `--dry-run`, `--include-all`, repair, link and reset.
- SQL must be a single SELECT/WITH: no semicolons, no write/DDL/session keywords, no comments. It is wrapped in `begin transaction read only … rollback`.
- All output is redacted.
- It makes one CLI call at a time.
- The fingerprint is saved outside the repo (directory mode 700, file mode 600).

It was tested only with a stub CLI (`tests/ws1-production-preflight.test.mjs`). The real CLI was never invoked.

`scripts/production/env-template.production` contains variable names and safe values only. Its test (`tests/ws1-env-template.test.mjs`) checks:
- every production-required or forbidden `launchConfig` key appears;
- all secrets are empty;
- with placeholders for the empty lines, the template gives 0 fatal and 0 warnings;
- the bare template is fatal.

## 5. Rollback drill: does eb43368 tolerate the 075 schema?

**Result: yes, for every dependency we could check.**

- **Static check** (`scripts/production/rollback-compat-check.mjs`, `tests/ws1-rollback-compat.test.mjs`):
  - Replays migrations to 046 and to 075 and reads eb43368 with `git show`: 83 files, 12 tables, 17 RPCs.
  - **0 BREAKING, 0 UNRESOLVED.** 10 REVIEW items each have a written verdict:
    - 047 guarded release functions;
    - 065 carrier-compatibility function (same 4 parameters);
    - 070 Stripe function (same parameters);
    - the 062 account-number NOT NULL, filled by a SECURITY DEFINER BEFORE trigger;
    - the 062 mirror triggers (exception-swallowing);
    - the 047 entitlements trigger;
    - the 069 CHECK constraint (a superset).
  - eb43368's user-scoped sign-up path is covered by the 059 column grants.
  - Seven mutation tests show the checker catches dropped or renamed columns, dropped RPCs, revoked EXECUTE, revoked sign-up grants, new triggers and new CHECKs.
- **Runtime check** (`tests/ws1-rollback-compat-runtime.pglite.test.mjs`, PGlite with the real migrations 000–075):
  - eb43368's sign-up statements succeed as `authenticated`, and an account number is assigned and registered.
  - All 18 eb43368 RPC call shapes resolve and are executable by `service_role`.
  - Assign → mark pending → cancel works; the mirror row is written; the 047 guard refuses a release clock for an entitled household.
- **Not proven:** booting the eb43368 server itself against a 075 database. That needs a real PostgREST and Supabase Auth, and there is no local Supabase stack. The HTTP and RLS layer stays covered only by the static check and the D7/R1 runbook drill.

## 6. Cross-review (B3 proof, 075, and the media-stream hardening in 14bd3aa)

| # | Severity | Finding | Action |
|---|---|---|---|
| F-1 | Medium (availability; no spend) | **The cap can be held about 3× longer than the 10 s timeout suggests.** `services/liveMonitoring/mediaStreamServer.js:47` and `:54` use `ws.close()`. A client that never answers the close frame keeps its slot until ws's 30 s close timeout. Measured locally: 3 sockets stayed in `wss.clients` for about 35 s with a 0.3 s start timeout. So an attacker socket holds a slot for about 40 s. With no per-IP limit, about 10 connections a second from one host keep the 400-socket cap full, and genuine streams get 1013 (monitoring blind; calls still delivered). Over-cap sockets also stay counted while closing | **Not fixed (file not owned).** Patch: use `ws.terminate()` at :47 and :54, and in the handler's unauthorised/malformed-start close paths (`mediaStreamHandler.js:459/513/520`).
