## 4. Grandfathering proof

Real `/billing/webhook` with genuine signatures, and real 070 SQL in PGlite, with `STRIPE_PRICE_ID` = the new Price, the old Price archived, the gate paused and the customer not on the allowlist:
- Subscription creation, 3 renewals, `invoice.paid` and `price.updated` (archived) produce:
  - the **same single** entitlement;
  - RPC calls that carry the subscription's own old Price;
  - provisioning kept "active";
  - `subscriptions.stripe_price_id` = the old Price.
- `past_due` keeps access. Only `canceled` ends it.
- The live function definition references `p_stripe_price_id` only to store it.

Static checks:
- Every `STRIPE_PRICE_ID` read is one of: new checkout, offer, metadata, config, or the admin MRR estimate.
- **No code compares a Price id** to grant or revoke access.
- No code calls `subscriptions.update`, subscription items or price edits.
- Both portal sessions pass only `{customer, return_url}`.
- With `PLAN_PRODUCT_MAP` set to the new Price only, the old Price resolves to Standard.

Not code-enforceable (console checks for Andrew):
- Stripe Portal "switch plan" must be **off**.
- **Archive, not delete**, the old Price.

Reporting findings for WS2 (not entitlement issues):
- `database/adminMetrics.js` estimates MRR as `STRIPE_PRICE_ID` × count.

Both overstate revenue and margin for £4.99 subscribers.

## 7. Assumed WS2 contract (`GET /admin/api/financial/customer-profitability`, `contractVersion: "ws2-profitability-v1"`)

```
{ contractVersion, generatedAt, period:{label,start,end}, currency:"GBP", basis,
  totals:{ customers, revenueNetGbp, attributableCostGbp, marginGbp, marginPct, projectedMarginPct },
  customers:[{ householdId, accountNumber, segment, channel, priceLabel, grandfathered:boolean, joinedAt,
    revenue:{ grossGbp, netGbp, basis:"actual|estimated" },
    cost:{ attributableGbp, telephonyGbp, aiGbp, smsGbp, numberRentalGbp, basis },
    margin:{ actualGbp, actualPct, projectedGbp, projectedPct },
    allowance:{ usedPercent, remainingGbp, budgetGbp, topUpsGbp, resetsAt },
    flags:[ "heavy_user"|"loss_making"|"loop_suspected"|"unusual_destination"|"fraud_signal" ] }],
  providerReconciliation:{ available, reason?, rows:[{ provider, providerSpendGbp, ledgerGbp, differenceGbp, differencePct, status:"ok|warn|mismatch", basis }] },
  signals:[{ severity:"red|amber|info", title, detail, accountNumber }],
  recommendations:[{ title, detail, confidence }] }   // advisory text only
```

How the page handles this:
- Numbers may be numbers or numeric strings.
- Any missing field shows "—".
- A different `contractVersion` produces a visible warning.
- An unavailable source is shown as unavailable, never as zero.

The page also reads these existing APIs: fortress overview, usage-safety, ops events and the control-centre summary.
