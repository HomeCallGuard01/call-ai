## A. Contract for WS3: customer allowance state (`GET /api/v1/me/allowance-state`)

- **Auth:** `requireAuthApi` + `requireEntitlement`, the same as `/api/v1/me/allowance`. The household always comes from the session; the route takes no parameters.
- **Router:** added to `routes/allowance.js`, which `server.js` already mounts. No `server.js` change is needed.
- **No £ figures are ever sent to the customer.** Only states, booleans and whole percentages. This matches the existing DT-2 rule: Fortress £ are HCG cost, not a customer price.
- **Unavailable is explicit.** If the state can't be read, `state` is `"unavailable"` and every boolean is `null`. A missing figure is never reported as protected.

### A.1 Response (HTTP 200)

```json
{
  "allowanceState": {
    "version": 1,
    "state": "normal",
    "percentUsed": 42,
    "screeningActive": true,
    "unknownCallersDelivered": true,
    "trustedCallersDelivered": true,
    "reserveRemaining": { "trustedPercent": 100, "unknownPercent": null },
    "serviceLimited": false,
    "periodStart": "2026-10-01T00:00:00.000Z",
    "resetsAt": "2026-11-01T00:00:00.000Z",
    "since": "2026-10-09T08:12:00.000Z",
    "thresholds": { "screeningLowPercent": 80, "continuityLowPercent": 80 },
    "lastRefusal": null
  }
}
```

| Field | Type | Meaning |
|---|---|---|
| `version` | `1` | Contract version. Any breaking change bumps it |
| `state` | enum, below | The household's deterministic allowance state |
| `percentUsed` | int 0–100 or `null` | Share of the period **screening budget** (plan budget + top-ups + adjustments) that is used or reserved by calls in progress. Reservations count as used, so this never understates use |
| `screeningActive` | bool or `null` | A new unknown call admitted now **would be screened** (stream, transcription, AI, warning SMS). False from `screening_paused` onwards |
| `unknownCallersDelivered` | bool or `null` | A new unknown caller would be **connected**, screened or not |
| `trustedCallersDelivered` | bool or `null` | A new trusted (contact) caller would be connected |
| `reserveRemaining.trustedPercent` | int 0–100 or `null` | Trusted continuity reserve left. `null` when the profile has none |
| `reserveRemaining.unknownPercent` | int 0–100 or `null` | Unscreened-delivery reserve for unknown callers left. `null` when the profile has none (the current default, see §C) |
| `serviceLimited` | bool | The service-wide emergency stop (kill switch or breaker) is engaged. New calls are refused for every customer |
| `periodStart`, `resetsAt` | ISO 8601 or `null` | The Fortress budget period |
| `since` | ISO 8601 or `null` | When the household entered `state` (from the transition log). `null` before the first transition is recorded |
| `thresholds` | object | The configured warning thresholds, so the app never hard-codes them |
| `lastRefusal` | `{ "reason": string, "at": ISO }` or `null` | The last call Fortress refused for this household this period. `reason` is a machine code (for example `household_budget_exhausted`, `household_hold`) |

### A.2 States (evaluated top to bottom; the first match wins)

| `state` | Condition (deterministic, SQL `fortress_household_allowance_state`) | Screening | Unknown callers | Trusted callers |
|---|---|---|---|---|
| `unavailable` | The state could not be read (DB down, migration missing, timeout) | `null` | `null` | `null` |
| `held` | A household financial hold is set (admin, fraud or automatic) | no | refused (busy) | refused (busy) |
| `hard_ceiling` | Screening budget can't fund a call, **and** neither continuity reserve can fund one | no | refused (busy) | refused (busy) |
| `continuity_low` | `continuity`, and ≥ `continuityLowPercent` of a continuity reserve that is in use is spent | no | per reserve | per reserve |
| `continuity` | The screening budget can no longer fund even an unscreened call. Calls continue only from the continuity reserves | no | only if the unknown reserve has room | only if the trusted reserve has room |
| `screening_paused` | The budget can't cover a new screened call's **worst case** (first lease + the full 30-minute monitoring window). Calls are still delivered, unscreened, from what is left of the budget | no | yes, unscreened | yes |
| `screening_low` | ≥ `screeningLowPercent` of the screening budget used or reserved | yes | yes | yes |
| `normal` | Otherwise | yes | yes | yes |

`serviceLimited: true` is reported alongside any state. It is not a state, because it is global and temporary.

### A.3 Ops events and push hooks

Each **transition** is recorded once, in the database, by `fortress_record_allowance_state(household, now)`:
- a row in `fortress_allowance_state_log`;
- an `fc_events` row, rule `allowance_state_changed`, with `{from, to, periodStart}`. The level is `info` (`normal`, `screening_low`), `warning` (`screening_paused`, `continuity`, `continuity_low`) or `critical` (`hard_ceiling`).

It runs after every authorisation and settlement, fire-and-forget (`services/containment/containment.js`). It never blocks or changes a call decision. The JS hook `onAllowanceStateChange({ householdId, from, to, state })` is where WS3 / ops attach push or ops-event delivery. **Event emission only. No SMS is sent.**

## 0. Summary

**What changed:**
- **Migration 076** (DRAFT):
  - a separate, bounded **unscreened-delivery reserve** for unknown callers. Its default is £0, which is exactly today's behaviour;
  - a deterministic per-household **allowance state** in SQL;
  - a transition log plus `fc_events`;
  - `GET /api/v1/me/allowance-state` (contract §A).
- **Migration 077** (DRAFT): the database itself now refuses any top-up credit that could create exposure beyond top-up revenue.
  - Disputes, and now **partial** refunds, reverse the credit.
  - A refund of credit that was already spent puts the household on hold.
- **Profitability read model** plus an admin router factory (contract §B, not mounted).
- **Deterministic PGlite scale simulation** (`scripts/sim/fortress-scale-sim.mjs`).
- **Offline provider reconciliation calculator.**

**Headline findings (all quantified below):**
1. **The recommended global caps cause an outage at scale.** `global_daily_absolute_max_gbp = 25` (cost-limits §3.4) trips the latching breaker:
   - with **genuine traffic alone** at N = 1,000, at hour 4.7, refusing 80% of genuine calls that day;
   - at N = 1,000 with 10% abusive households, in the **first minute**;
   - at N = 100 with 10% abusive households, at hour 10, refusing 64% of genuine calls.

   It is safe only at N ≤ about 25 (the cohort it was written for). A scaled policy (§4) removes the false trips. It still bounds abusive households at their £2.00 hold, and a 50% mass compromise still trips the breaker within 0.4 h.
2. **No production code feeds provider actuals back into Fortress** (`fc_record_actual` has no caller).
   - Estimate-vs-actual is protected only by the conservative estimate (×1.1, SDK leg at list).
   - The new offline reconciliation calculator (§5) is the detective control until a price import exists.
3. **"Trusted callers are never cut off" and "no unlimited cost path" cannot both hold under `**21*`.** Every trusted minute is on HCG's Twilio bill. §2.4 gives the £ options; Andrew decides.
4. **The £3.00 budget is about the typical household's monthly demand.** A typical household costs £2.93/month on the Fortress basis.
   - In a 7-day N = 1,000 simulation, 48% of typical households were on pace to exhaust **screening** within the month, and 30% to reach the ceiling.
   - All heavy and very-heavy households were on pace to do both.
   - The budget protects HCG, but it will visibly pause screening for many genuine customers.

## 2. Allowance-exhaustion state model

### 2.1 What Fortress did before 076 (verified on real SQL)

| Situation | Unknown caller (`wantsMonitoring` = true) | Trusted caller (`deliveryTrusted`) |
|---|---|---|
| Budget ≥ first lease + 30-min window (£0.3376 at default rates) | Admitted **monitored**; the whole window is reserved up front | Admitted from the budget |
| Budget < £0.3376 but ≥ one lease (£0.0713) | Admitted **unmonitored** (`monitoring_budget_insufficient`) from what is left of the budget | Budget |
| Budget < one lease | **Refused** (busy; `household_budget_exhausted`), because the profile scope is `trusted_only` | Admitted from the delivery reserve (£0.50 recommended) |
| Budget + reserve spent | Refused | **Refused** (busy) |
| Live trusted call when the budget runs out | — | Continues to its provider backstop. Its worst case was reserved as contingent at admission, so other calls cannot take it. Proven: "renewed to its provider backstop, not cut for budget" |
| Held / kill switch / breaker | Refused; live calls end at lease end | Refused; live calls end at lease end |

### 2.2 The 076 change

- A **separate, bounded unscreened reserve** (`fc_budget_profiles.unscreened_reserve_gbp`, 0–£20, audited setter `fortress_set_unscreened_reserve`).
  - It funds unknown callers past the budget, unscreened.
  - It never funds monitoring, SMS or AI, and never trusted calls.
  - It has its own reserved and consumed counters, plus an invariant check.
  - Its worst case is contingent on itself, so it cannot drain the budget or the trusted reserve.
- **Default £0**, so every decision is identical to 067. The whole 067 regression suite passes with 076 applied.
- States and thresholds: contract §A.2. Thresholds come from the audited `fortress_allowance_policy` (0.80/0.80). `screening_low` only appears when the budget is above £1.69 (0.20 × B must exceed £0.3376). At the recommended £3.00 it appears at 80%.
- The transition log, `fc_events` and the JS hook: §A.3.
- The rollback refuses while any unscreened spend exists, and restores 067's function bodies verbatim. Tested by comparing `pg_proc` with a database that never saw 076.

### 2.3 Worst case per customer per period (Fortress basis)

Worst case = B + T + U + E + overrun (≤ one lease per pool, about £0.07–£0.12):
- B = budget, plus top-ups (each bounded by 077);
- T = trusted continuity reserve;
- U = unknown unscreened reserve;
- E = essential pool.

Billed cost is about 0.75 × Fortress today (SDK leg billed £0), and ≤ Fortress ÷ 1.1 if the SDK leg starts billing at list.

These options use B = £3.00 and E = £0.10. Contribution is measured against the cost-limits LOSS line (£3.37 billed usage room at £5.99 Stripe).

|---|---|---|---|---|---|---|---|

**Conflict C1, stated plainly.** Under `**21*` unconditional forwarding, every trusted minute costs HCG about £0.0086 billed. The only ways to deliver trusted calls without that cost are to reject the call or have the customer switch forwarding off (C5 network routing removes the conflict).
- So "trusted callers must not be deliberately cut off" can only be honoured **up to T**.
- After T, a trusted caller hears busy until the period resets, an admin adjusts the budget, or a top-up is bought.
- The hold, kill switch and breaker also end live trusted calls by design.

## 4. Scale simulation (PGlite, real migrations + recommended policy SQL)

**Conclusions:**
- Per-customer max cost vs revenue:
  - an extremely heavy household is stopped at ≤ £2.25/day by the hold;
  - simulated maximum £2.19 Fortress, £1.99 billed with the SDK leg at list;
  - ≤ £3.70 per period on the Fortress basis if every hold is released.

  That compares with £4.53 net monthly revenue (£5.99 Stripe). Modelled billed cost was always ≤ the Fortress estimate.
- **The recommended caps block normal traffic at N = 1,000** (and at N = 100 with 10% abusers). The cause is the £25 absolute daily ceiling. The hourly (0.24 × N), exposure (0.20 × N) and worst-case (0.80 × N) caps did not false-trip.
- **Recommended scaling (DECISION D-4):**
  - set the absolute daily ceiling to about 0.60 × N for the planned cohort, and raise it deliberately per stage;
  - set `global_active_households_per_call` to 2 at N ≥ 500;
  - keep the hourly cap at 0.24 × N. It is what stops a mass compromise.

  Daily ceiling at stage N: 25 → £25; 100 → £60; 250 → £150; 1,000 → £600. The global worst day is then about 0.6 × N + unattributed £0.25.
- `fc_refresh_entitled_count` counts every active entitlement. Inflated sign-ups would raise the scaled caps, which is why the absolute ceiling is set per stage rather than left at 1,000.

## 5. Provider billing delay and reconciliation (`services/finance/providerReconciliation.js`)

Offline, with no API calls. Fortress calls are matched to provider usage records (a Twilio call and its SDK child leg via `parentSid`; streams and transcription via `callSid`; USD converted at the register FX rate). The calculator flags:

| Flag | Meaning | Level |
|---|---|---|
| `undercount` | Billed above the Fortress estimate, by any amount | critical |
| `model_gap` | Differs from the register model by more than 20% (configurable) | warning |
| `unmatched_provider` | Billed but never authorised by Fortress (outage fallback, bypass, master token) | critical |
| `missing_provider` | No provider record after the billing-delay window (default 24 h) | warning |
| `pending` | Inside the billing-delay window; not judged yet | — |

Unknown currencies are never guessed. Tests use the synthetic fixture `tests/fixtures/ws2-reconciliation/fixture.json`. They include the case where the SDK leg starts billing: `model_gap` fires, but Fortress is not undercounted, because it already budgets the leg at list.

**Recommendation:** run it daily against a Twilio Usage/Calls export and an OpenAI usage export, and alert on any critical flag. Later, wire Twilio call prices into `fc_record_actual` (G-1).

## 6. Degraded mode (analysis only; production default unchanged: D3 = reject)

**Today.** If the Fortress RPC fails or times out (1.5 s), every new call is refused, trusted ones included. Live calls admitted by this instance are ended locally after lease + 60 s.

**A bounded trusted-only option.** The code exists, but only for test/dev (`FC_DEGRADED_MODE=bounded`). It would use per-instance in-memory caps: ≤ 2 concurrent, ≤ 20 calls/h, 600 s `timeLimit`, ≤ 15 min outage. Calls are journalled and adopted into the ledger on recovery (`fc_adopt_degraded_call`).
- Worst case per instance: ≤ 20 × (660 s at £0.01179/min + £0.0006) ≈ **£2.61/h**, and at most about £0.65 per 15-minute outage at 2 concurrent.
- With R instances and K outages per day: ≤ R × K × £0.65.
- It is bounded, deterministic and needs no DB.

**But:**
1. Contacts, households and entitlements live in the **same Supabase** as Fortress. In a real DB outage, `/voice` cannot resolve the household or the trusted list. So "trusted-only" can only be honoured if a local contact and household cache exists, which it does not today.
2. The envelope is per instance and not per household. One flooded household could take all 20 calls.
3. The calls are adopted after the fact, so a household's period ceiling can be exceeded by up to the envelope.

**Recommendation:** keep **reject** for the cohort (≤ 25). Revisit bounded trusted-only after all of:
- (a) a signed local cache of households and trusted numbers;
- (b) a per-household cap of 1 degraded call;
- (c) the envelope counted against the household's reserve on adoption;
- (d) Andrew approves a £ ceiling per outage.

**Cost of rejecting:** trusted callers hear busy for the length of the outage. That is conflict C2, stated, not resolved.

## 8. Open risks

- **G-1:** no online actuals. Undercounts are detected only by the offline reconciliation.
- **G-2:** no sweeper watchdog. A dead sweeper means the provider timeLimit is the only bound, and the caps fall to their floors after 26 h.
- **G-3:** Layer B and the abuse layer fail open.
- **G-4:** in-memory counters reset on restart.
- **G-6:** Twilio has no spend cap, and the master token is in the backend (provider checklist B4). These are the largest residuals and sit outside any code bound.
- **G-7 / G-8:** top-up reversals are skipped while the flag is off (`billing.js` / `mobileApi.js`; lead).
- **G-9:** recommended global caps cause an outage at N ≳ 25 with abusers, and at about 250 without.
- 076 adds one fire-and-forget RPC per call decision. `FC_ALLOWANCE_STATE_EVENTS=false` disables it.
- Revenue in the profitability model is configuration-backed: the live price map, plus Apple £4.99 and the 30% fee model. It reads no invoices. Store prices outside GBP are not modelled.
- Simulation inputs are the register's **illustrative** usage profiles. No measured usage distribution exists.
