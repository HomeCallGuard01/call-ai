# Mobile call-delivery security review (30 Sep 2026)

Scope: Voice access tokens, client identity, push registration, app-to-backend delivery routes, and secrets and logs in the app. This was a code review only: **no testing against production**, and no destructive or active probing.
For Claude A's wider security review. Fixes are on `readiness/android-call-delivery` (not deployed).

| # | Finding | Severity | Status |
|---|---|---|---|
| S1 | **Voice token grants outgoing calls; the TwiML App's Voice URL is unknown.** `buildVoiceAccessToken` sets `outgoingApplicationSid`, so any entitled household, or anyone holding a leaked token, can place a Voice SDK call and Twilio will fetch the TwiML App's Voice URL. The route it was configured with in Aug (`/voice-sdk-outbound-not-supported`) **never reached main**. If the URL was ever pointed at `/voice`, a forged `To` makes HCG treat it as an inbound call to any household: paid monitoring (denial-of-wallet), a ring on the victim's app, fake Activity | High (conditional on config) | **Mitigated in code:** `/voice` rejects any `client:`-originated request before any lookup, write or paid step (unbilled `<Reject>`); the fallback route is restored (reject only). **Action (Andrew, read-only):** check the TwiML App's Voice URL in the Twilio Console. **Later:** try removing `outgoingApplicationSid` (needs a device test) |
| S2 | **A leaked access token gives lasting call interception.** A token (1 h TTL) can register *any* device's push token under `household_<id>`. The binding lasts about a year after the token expires. That device rings for, and can answer, the household's calls. HCG cannot list or evict bindings, and sign-out only unregisters the signing-out device | High (needs a leaked token) | **Open, design needed.** Proposed: identity epoch `household_<id>_<n>`. `<Dial><Client>` always uses the current epoch; "sign out all devices", a password reset or a suspected compromise bumps it, so old bindings are never dialled. Needs a migration + token + routing change + app compatibility plan. Tokens are never logged (verified) |
| S3 | **Unsigned Twilio webhooks.** `/voice` and `/call-delivery-failed` don't enforce `X-Twilio-Signature` (shadow only). Forged POSTs can create fake calls rows and Activity, trigger "approved call delivery failed" support emails, and run DB reads | Medium (integrity / denial-of-wallet) | Pre-existing, Claude A's area. **My telemetry does not amplify it:** DB writes and endpoint-health reads happen only for validly signed requests; unsigned requests get log lines only |
| S4 | **Twilio REST amplification via app invite reports.** An authenticated household could post arbitrary well-formed CallSids; each unknown SID caused a `calls(sid).fetch()` against the account whose REST concurrency live call handling shares | Medium | **Fixed:** per-household rate limits (240/h on invite reports) plus a 10-min per-household negative cache; malformed SIDs never reach Twilio |
| S5 | **Unbounded authenticated app routes** (`/voice/token`, `/voice/registered`, invite reports, device-readiness) grow tables and logs without limit | Medium (denial-of-wallet) | **Fixed:** per-household fixed-window limits, 429 + Retry-After, bounded memory (fails closed). In-memory per instance (still bounded with N instances) |
| S6 | Unauthenticated `/debug/purchase-beacon` (and the app's `/debug/voice-beacon`, which has no handler, so 404s) | Low | Payload bounded (≤600 chars) but no rate limit, so log-volume abuse is possible. Recommend a global per-IP limiter (Claude A) and removing the dead voice beacon from the app |
| S7 | Identity spoofing on token issuance | — | **Not possible:** identity comes only from the authenticated household (`req.household.id`), never the request (tested) |
| S8 | Wrong household ringing after account switch | — | Fixed on `p0/call-delivery-resilience` (unregister on sign-out + wrong-identity invite reject); device test P9 required |
| S9 | Secrets in the app bundle | — | **None found.** Only public-by-design values are compiled in (Supabase URL + anon key, RevenueCat iOS public key, API base URL). No keys or credentials tracked in `mobile/` |
| S10 | Sensitive data in logs | Low | App: logs call SIDs and error objects, never tokens (verified). Server telemetry: household id + call SIDs only; caller numbers, names and transcripts are impossible by schema (tested). Pre-existing: historical Railway logs may hold transcript text (separate finding) |
| S11 | Replay of Twilio webhooks | Medium | Twilio signatures don't include a timestamp, so even enforced validation allows replay of a captured request. Consider idempotency on CallSid for writes (Claude A) |

## Denial-of-wallet properties of the new telemetry
- Server events are bounded by genuine (Twilio-signed) inbound calls: about 9 rows and 3 small reads per call.
- App events are bounded by the per-household rate limits.
- Rows are content-free and each `detail` is at most 2 KB. Retention is still to be decided (90 days proposed).
